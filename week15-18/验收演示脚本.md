# 验收演示脚本

> 目标：5 分钟内把主链路走完，不翻车；万一翻车，30 秒内切到预案。
> 演示前 10 分钟按“一、演示前检查”过一遍。

## 二、演示顺序（约 5 分钟）

### 0. 开场（15 秒）

“这是手机屏幕外观缺陷检测系统，上传照片后自动找六类缺陷，并把记录存下来。
我用管理员账号登录，先走一遍检测。”

### 1. 登录（20 秒）

- 打开 `http://127.0.0.1:5000`，展示登录页；
- 说一句：演示账号 admin / 123456，普通用户 user / 123456；
- 用 admin 登录，进入检测中心。

**预期**：进入检测页，右上角引擎状态变绿。

### 2. 单张检测（60 秒）

- 把 1 张测试图拖进上传区；
- 指一下置信度 0.25、屏幕区域聚焦已勾选；
- 点【开始检测】；
- 结果页出现后，依次指：结果图的框和类别、4 个指标卡、缺陷明细；
- 点【下载结果图】，再点【导出 CSV】。

**话术**：“框的颜色对应类别，框上方是类别和置信度；每条明细有置信度和位置；
CSV 带 BOM，Excel 打开中文不乱码。”

**预期**：1–3 个框，结果页正常，下载和导出各弹一次保存。

### 3. 批量检测（40 秒）

- 返回检测页，一次选 3 张图；
- 点【开始检测】，指一下进度“第 x/3 张”；
- 完成后跳到第一张结果页；
- 说：“其余两张在历史记录里，每张一条记录。”

**预期**：进度逐张走，历史里新增 3 条。

### 4. 历史记录（40 秒）

- 打开历史记录；
- 日期留空，“缺陷情况”选“有缺陷”，点【查询】；
- 翻一页，点一条【查看】；
- 说：“普通用户只能看自己的；管理员可以按用户筛。”

**预期**：列表和总数同步变化，详情能打开。

### 5. 数据统计（35 秒）

- 打开数据统计；
- 指 4 个卡片：检测总数、缺陷总数、今日检测、平均耗时；
- 指柱状图、饼图、趋势图；
- 说：“统计只算当前账号能看到的记录；管理员看全部。”

**预期**：4 个卡片有数，三张图有数据。

### 6. 个人资料（20 秒）

- 打开个人资料，改一个昵称，点【保存昵称】；
- 说：“侧边栏和用户列表会同步更新。”

**预期**：提示保存成功，侧边栏昵称变化。

### 7. 管理员功能（30 秒）

- 打开用户管理；
- 指用户列表的检测次数、缺陷数；
- 点某个用户的【查看记录】，跳到历史页并自动筛选；
- 回检测页，指【把当前置信度设为默认】。

**预期**：用户列表有 3 个账号，查看记录能跳转。

### 8. 权限对比（30 秒）

- 退出，用 user / 123456 登录；
- 说：“普通用户没有用户管理，历史里也看不到别人的记录。”

**预期**：侧边栏没有用户管理，历史只有 user 自己的记录。

### 9. 收尾（20 秒）

- 回到 PPT 或报告第 7 章；
- 说一句真实案例：“同一张真实碎屏图，改进前 26 个框，改进后 3 个框；
  但真实图只有一张，不能算真实 mAP。”

## 三、翻车预案

| 现象 | 现场处理 |
|------|----------|
| 页面打不开 / 端口占用 | 换 `python run.py --port 5001`，用新端口打开；或提前开两个端口 |
| 模型未加载 / 检测 503 | 看终端日志；确认 `models/best.pt`；重启 `python run.py`；仍不行就切到 `site/demo.html` 静态演示 |
| 检测很慢 / 卡住 | 说“第一次加载模型会慢几秒”，等；超过 30 秒刷新，改用单张 |
| 上传被拒 | 确认格式 jpg/png、< 20 MB、不是结果图；换一张准备好的图 |
| 统计页没数据 | 点“全部时间”；或换 admin；或先现场检测一张 |
| 下载没反应 | 浏览器可能拦截多文件下载；点一次，等保存框；或改用右键“链接另存为” |
| 投影分辨率导致布局变化 | 浏览器缩放 100%；提前在投影上试一次 |
| 完全跑不起来 | 用 `site/index.html` + `site/demo.html` 静态演示，配合 PPT 截图；说明本机环境问题，不硬撑 |

## 四、常见提问与回答

**Q1：mAP 0.99，真实场景是不是也这么准？**
A：不是。0.99 是合成测试集上的结果；真实照片只有一张，只能做案例分析。
真实场景需要补标注数据后重新评估，报告 6.3 节和测试报告 8.5 节都写了。

**Q2：为什么不用真实数据训练？**
A：课程期间收集不到上千张带标注的真实缺陷照片，六类凑不齐，标注也很慢。
所以先用程序合成把流程跑通，再用困难数据补真实场景；真实数据的接入方案在
详细设计 2.7 节，补 100–200 张就能微调。

**Q3：26 个测试够吗？**
A：覆盖了主流程、权限、异常和模型，但不够全面：没有并发压测、没有多浏览器全覆盖、
没有专业渗透。测试报告第 2.2 节明确列了不在范围内的内容。

**Q4：为什么用 YOLOv8n，不用更大的模型？**
A：课程演示看重能跑、能带走、能解释。n 只有约 6 MB，GPU 单张推理约 4 ms，
CPU 也能跑；更大的模型精度提升有限，但部署和演示成本高。

**Q5：误检从 26 降到 3，是不是调阈值调出来的？**
A：不是。单纯调阈值救不了：低阈值误检更多，高阈值漏检更多。
改进来自三处：困难数据、混合训练、ROI + 尺寸过滤。消融表在详细设计 7.4 节。

**Q6：为什么真实图只框住一部分裂纹？**
A：真实蜘蛛网裂纹分支很密，模型对细分支的响应弱，后处理也没有合并相邻框。
这是已知局限，改进方向是补真实裂纹标注、做框合并。

**Q7：系统能上产线吗？**
A：不能直接上。它是单机辅助检测原型：Flask 开发服务器、SQLite、没有 CSRF 和限流，
并发也没验证。上产线要换 WSGI、数据库、加安全和设备对接。

**Q8：两个人怎么分工？**
A：王周毅偏数据、模型、检测、接口、性能和报告；林城于偏需求、设计、前端、
记录/统计/资料/管理员、界面测试和手册；联调、缺陷修复、文档校对一起做。

**Q9：最大的难点是什么？**
A：数据。不是模型结构，也不是页面，是“从哪弄到带标注的缺陷图、怎么让模型学到
真实缺陷”。合成数据解决了“有没有”，困难数据解决了“像不像”，但真实数据仍然不够。

**Q10：如果再做四周，先做什么？**
A：补真实数据、重新评估，这是收益最高的；然后是裂纹框合并、CSRF/限流、并发和部署。
继续调参的收益已经不如补数据。
